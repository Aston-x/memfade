# 架构

## 为什么是 core + adapters

市面上的 QQ 机器人框架，编程语言和插件模型都不同：

| 框架 | 语言 | 插件模型 | 注入 prompt 的方式 |
|---|---|---|---|
| MaiBot | Python | SDK 装饰器 + 命名 Hook | `ctx.maisaka.context.append` |
| LangBot | Python | `BasePlugin` + `EventListener` | `event.default_prompt.append` |
| AstrBot | Python | `Star` + `@filter` | `req.system_prompt` |
| NoneBot2 | Python | `PluginMetadata` + Matcher | 无统一钩子，提供助手 API |
| Koishi | TypeScript | `apply(ctx, config)` | 无统一钩子，走 HTTP 侧车 |

如果给每个框架各写一份记忆系统，淡化算法一定会走样——
五种实现五个 bug，而且每加一个框架就多一份维护负担。

所以 memfade 的结构是：核心 `memfade/` 不知道任何框架的存在，
只依赖标准库；每个适配器只负责「翻译」：
把宿主消息翻译成统一格式、把记忆翻译回宿主上下文、
把宿主的 LLM 接到核心协议上。

Koishi 走 HTTP 侧车，是因为它是 TypeScript 生态——
与其用 TS 重写一遍淡化算法（必然走样），不如让核心只跑一份。

装上它的人要用的工具，必须跟着插件走，而不是留在开发者的仓库里。

## 写入前的两道闸门

抽取出来的候选要过两道闸才准入库。**两道都在代码里，不靠提示词。**

    LLM 抽取 ─▶ 主语纪律 ─▶ 找依据原话 ─▶ 对账闸门 ─▶ 阈值 ─▶ 落库
                (extract.py)   (guards.py)     (guards.py)   (engine.py)

**主语纪律**（`extract.filter_drafts`）解决「记的是不是关于这个人」：
主语是机器人自己 → 丢；是泛指词 → 换成真人或丢；不是人 → 丢。

**依据原话 + 对账闸门**（`memfade/guards.py`）解决「记的内容对不对」：

1. `find_evidence()`——在**用户自己说的话**里找这条记忆的出处
   （机器人说过的话是上下文，不是用户的证词）。匹配用「短句被长句覆盖的比例」：
   记忆是原话的改写（「今天只有一节课」→「季怡每天只有一节课」），
   Dice 只有 0.27，但宾语「一节课」原封不动，覆盖度就是 1.0。
2. `check_draft()`——拿依据跟内容对账：

   | 情况 | 判定 | 处置 |
   |---|---|---|
   | 内容带「今天/这次/刚才/当时」，却记成稳定事实 | 一次性情况 | 降级为事件 |
   | 内容有「每天/总是/永远」，依据里没有 | 模型自己加的断言 | 降级为事件 |
   | 依据是指令口气，且没有长期性证据 | 当次的吩咐 | 降级为事件 |
   | 内容带「暂时/被拦/卡住」 | 临时状态 | 不入库 |
   | 内容带「累/困/饿/烦」 | 临时情绪 | 不入库 |

**降级不是丢掉**：降级后信息还在，只是不再常驻注入，
交给淡化引擎自然淘汰——这正是淡化引擎该干的活。

**阈值卡在模型自己给的分数上**。种类区间（episodic ≤0.55 / semantic ≥0.40）
是**存储形态**的约束，只在落库那一刻夹一次；
提前夹会把模型给的 0.1 抬到 0.40，正好越过门槛——垃圾记忆就有了后门。

**出处留痕**：依据原话存进 `meta["quote"]`，面板上直接看得见。
抽取难免出错，但出错之后要能改：核心有 `edit_memory()`，
面板与 `/记忆 修正` 调它，运维脚本 `edit_memory.py` 也调它——
补救口不必整库清空。

## 热路径 / 冷路径

**热路径**（每条消息都跑）：`build_context()` → 召回 → 打分 → 组装。
纯同步，不含一个 `await`，不碰网络。实测在几千条记忆的库上是毫秒级。

**冷路径**（每 N 轮 / 定时跑）：抽取、摘要、整理。这些要调 LLM，走 async。

这个划分让核心在**同步宿主**（脚本、CLI）和**异步宿主**（几乎所有 bot 框架）
里都能直接用——同步宿主调热路径，异步宿主额外 await 冷路径即可。

## 存储

单文件 SQLite：

```sql
memories(id, scope_key, kind, content, summary, importance, strength,
         anchor_at, status, created_at, updated_at, last_recalled_at,
         recall_count, pinned, cross_scope, subject, predicate, object,
         source, superseded_by, content_hash, fts_tokens, meta, embedding)
```

* `fts_tokens` 是预计算的字符二元组串，FTS5 触发器保证索引与主表同步；
* `embedding` 是 float32 BLOB，numpy 在就用矩阵运算，不在就纯 Python；
* `meta` 是 JSON，装合并历史、来源等附加信息。

**升级路径**：`CREATE TABLE IF NOT EXISTS` 只建新表，**不会给已有的表加列**——
插件是装到别人机器上的，老库必须能被新版本直接打开。
所以开库时会比对建表语句与实际表结构，缺哪列补哪列，
并用 `PRAGMA user_version` 记下 schema 版本。

**搬迁路径**：`export()` 出的是 JSON（含强度与锚点等淡化状态），
`import_memories()` 能读回来——**记忆是用户的数据**，
换机器、换机器人、换框架都得能带走。不搬淡化状态的话，
搬过来的记忆会「重新变年轻」，该淡的又淡一遍。

## 作用域过滤只有一条

```sql
WHERE (scope_key = ? OR cross_scope = 1)
```

## 四条检索通道，以及为什么要单字兜底

| 通道 | 实现 | 什么时候用 |
|---|---|---|
| 全文 | FTS5 + 字符二元组 | 主力 |
| 单字兜底 | `LIKE '%字%'` + 命中率 | 全文一无所获、且查询短到像关键词 |
| 向量 | 余弦相似度 | 宿主配了嵌入模型 |
| 近期 | 写入时间倒序 | 候选来源之一，**不直接进上下文**（见下） |

**单字为什么不能塞进 FTS 索引**（试过，退了）：
同一个 FTS 表里混着单字，长文档涨的 token 比短文档多，
BM25 的长度归一化被带偏，长记忆被压得更狠——
「重要的长约定」会被「炸鸡」这种短条目反超。
所以单字走独立的 `LIKE` 通道，靠三道闸门防止它污染结果：
查询 ≤2 个汉字、命中 ≤20 条、主通道必须一无所获。

**查询词也要滤虚词**：「在的」「的是」这种全虚词二元组
几乎出现在每一句中文里，拿它们检索等于跟整本语料库匹配。
两个字符都是虚词的查询词直接丢掉（「存在」保留，「在的」丢掉）。

这条出现在**所有**读取路径上：FTS 检索、向量检索、近期召回、整理、
去重候选。没有第二条「找不到就退回全局」的路径。

跨会话共享（`cross_scope = 1`）必须显式开启——只有抽取器认定
「用户明确要求记住」时才会置位。

**相关度闸门常开**：召回、注入、面板解释三处同一口径——
候选必须**真的命中**（相关度 ≥ 底线）才算数。
以前这条闸门是「有向量能力才要求」，于是**没配嵌入服务的部署
每一轮都把最近几条塞进上下文**（就是「总提旧事」）。

**「刚聊过」的受限兜底**：中文里「那部番叫什么」这种指代满地都是，
词面一个都搭不上，但答案往往就是刚刚聊过的那条。
所以：只在查询**明显在指代**时放**一条**进来，且要求它是几小时内写入的。
指代词表里**不放「他/她/它」**——那等于没有闸门（「她喜欢吃什么」也会命中）。

## 一次调用的完整链路

```
入站消息
   │
   ├─► 解析作用域（平台 + 会话类型 + 会话 ID）
   │      群 1127155154  →  qq:group:1127155154
   │      私聊 1738157278 →  qq:private:1738157278
   │
   ├─► 热路径：召回
   │      FTS5 二元组检索  ─┐
   │      单字兜底检索     ─┤
   │      向量检索         ─┼─► 候选集合
   │      近期写入         ─┘
   │
   ├─► 打分
   │      rel / importance / strength / recency / freq
   │      + 与首条命中共享关键词的关联加成
   │
   ├─► 分层
   │      ACTIVE      → 事实层
   │      FADING/GIST → 回声层（限量 + 过时标记）
   │      ARCHIVED    → 丢弃
   │
   ├─► 预算裁剪 → 渲染成文本
   │
   └─► 注入宿主上下文 + 强化被注入的记忆

（冷路径，每 N 轮）
   入站消息 → 剥掉引用与转发 → 抽取候选 → 主语纪律 → 去重 → 落库
   （定时）
   全库 → 衰减重算 → gist 压缩 → 合并重复 → 矛盾仲裁
```

**主语纪律**在入库前拦一道：主语是机器人自己（机器人认领了主人的记忆）、
主语是「用户/对方/他/她」（没法做矛盾检测）、主语不是人（作品名、赛事名、
链接名这类公共知识）——一律不入库。**提示词会求，代码更要拦**：
提示词说「别记自己的事」，模型偶尔还是会犯；犯一次，
主人的记忆库里就多一条「机器人自己看了什么番」。

**引用与转发不是用户的话**：宿主把「被引用的那条消息」拼进用户正文，
抽取器对着这份文本抽取就会把机器人自述、群公告当成用户的事。
所以抽取前先剥掉；引用留作**上下文行**（用来判断「他」指谁），
转发整块丢掉。

## 注入时机：为什么不是「收到消息就注入」

宿主把「注入上下文」这件事放在**模型请求之前**，而不是「消息到达时」。
原因有二：

1. 消息到达时，会话可能还没建立，注入会失败；
2. 只有在请求构造阶段才能**直接改写真正发给模型的 Context Items**——
   写进聊天历史的话，会被上下文的裁剪逻辑顺手丢掉。

以 MaiBot 为例，钩子选在 `maisaka.planner.before_request`
（规划器）与 `maisaka.replyer.before_model_request`（回复器）：
两次模型请求各注入各的，互不干扰，而且都有现成的 `session_id` 可当作用域键。

## 各适配器的注入点

| 适配器 | 注入点 | 作用域键 | 指令 | 模型可调的工具 |
|---|---|---|---|---|
| MaiBot | 规划器改 `items`；回复器追加 `extra_prompt` | `session_id` | `/记忆` `/记住` `/忘掉` | `remember_something`、`recall_memories` |
| LangBot | `event.default_prompt.append(Message(role="system"))` | `session_name` | `记忆 状态/搜/整理/置顶`、`记住`、`忘掉` | — |
| AstrBot | 改写 `request.system_prompt` | 群号 / 用户号 | `记忆 状态/搜/整理/置顶`、`记住`、`忘掉` | — |
| NoneBot2 | 无统一钩子 → 提供 `build_context(event)` 助手 API | `get_session_id()` | `/记忆` `/记住` `/忘掉` | 公开 API |
| Koishi | 无统一钩子 → HTTP 侧车返回现成文本 | 群号 / 用户号 | `记忆` `记忆.搜/整理/置顶`、`记住`、`忘掉` | 侧车 `/recall` |

指令面在四个适配器里是**齐的**：查状态（且列出内容，不只给数字）、
检索（必须真命中）、整理、置顶、记住、忘掉。

## 验证程度

不吹牛，逐个说清楚每个适配器被验证到哪一步：

| 适配器 | 验证方式 |
|---|---|
| MaiBot | 实机部署在许杏玖上；宿主自己的反序列化器验证注入的 item |
| LangBot | 真的 `langbot-plugin` SDK，9 项测试跑在真 SDK 上（含**组件清单的真 SDK 发现**） |
| AstrBot | 真的 AstrBot SDK 源码，ast 静态核对 API 面 + 桩件测逻辑 |
| Koishi | 真的 koishi@4.18，`tsc` 类型检查 + 6 项行为测试（起真的 Python 侧车） |
| NoneBot2 | 真的 nonebot2，测试跑在真 SDK 上 |

另外有一条**零配置验收**（`memfade_tools/acceptance.py`，18 项）：
不连 LLM、不连嵌入服务，把存储 → 写入 → 检索 → 会话隔离 → 注入 →
画像 → 淡化 → 整理 → 导出导入 → 体检整个闭环跑一遍。
它是「装上就绪」这句话唯一的证据——每一环都可能悄悄坏掉，
而插件照样能加载、界面照样能打开。
